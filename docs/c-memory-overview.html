c-memory：Claude Code 的个人记忆闭环

三条独立管线并行运行：语义/程序性记忆闭环（观察 → 提炼 → 注入，把工具调用沉淀成带置信度的 行为习惯与项目事实）、情景记忆滚动总结（把对话本身滚动总结成"上次聊到哪了"，解决重开会话丢上下文的问题）、 以及流程挖掘（识别反复出现的多步骤操作序列，结合下一轮用户反馈判断这次复现是否真的有效，稳定复现后引导转成 Skill）。 外加一个轻量工具最近会话记录：退出时把 session_id 记下来，方便手动 --resume 时查。 全程个人单机运行，无需人工整理。以下是当前真实代码状态的完整机制说明，非规划稿。

2026-07-28：提示词字段结构完全对齐得物

curl 拉取得物开源复刻仓库 scripts/analyze_instincts.py / extract_memories.py 的真实 prompt 源码后确认： 得物的 id/name 字段是 LLM 直接产出的英文 kebab-case，不是本地对文本 slugify 出来的——这正是 之前 id 一直是中文的根因。已把 prompt 和内部字段名都改成一致：

instincts: {"id": "read-before-edit-pattern", "trigger": "...", "action": "...", "domain": "workflow", "evidence": "..."} project_facts: {"name": "uses-pnpm", "description": "...", "body": "...", "type": "project", "keywords": [...]}

_sanitize_id() 校验 LLM 给出的 id/name 是否为合法英文 kebab-case，合法直接用，不合法（LLM 未遵守指令、或走 NullProvider 规则兜底路径）才退化为本地 _slugify()。domain 收窄为固定枚举 workflow / testing / git / code-style / project-context，project_facts 的 type 扩成 project / feedback / error / workflow 四类，并加了排除清单（"不要提取一次性临时操作/过细代码变更/显而易见的通用知识"）。

未对齐之处：仍是一次 analyze() 调用同时产出 instincts 和 project_facts（得物是两个脚本两次独立调用）， 出于成本/延迟考虑保留合并调用；project_facts 额外要求的 keywords 字段是本项目自己为语义去重加的，得物原版没有。

已移除：按批次衰减（_decay_missed_instincts） 原逻辑"本次候选没命中的活跃 instinct 一律 confidence −0.05"建立在"每次都看得到全会话历史"的前提上。 改成小批量增量后继续按批次衰减会让几乎全部 instinct 快速跌破 deprecate 阈值——已移除该调用，衰减机制待重新设计 （候选方案：按 last_seen 距今天数做时间维度衰减）。

04 注入 · inject.py（SessionStart）

阅读目的：确认最终打到 stdout、被 Claude Code 自动注入上下文的内容具体由哪几段拼成，以及孤儿 session 补漏何时发生。

SessionStart（含 /compact 触发的那次）是官方确认 stdout 会被直接注入上下文的事件之一。内容按顺序由三段拼接：

project-recap 情景记忆（新增，排最前）

读 memory/project-summary.md，非空整段作为 [project-recap] 注入——"我们做到哪了"比习惯/事实更适合先读。

habit 确定性阈值过滤

storage.list_promoted_instincts() 直接读 instincts/*.md，confidence≥0.7 且未 deprecated 的全部， 按 confidence 降序，上限 30 条，不经过向量召回。

project/feedback/error/workflow 相似度排序截断

build_query(cwd) = 项目名 + git log --oneline -3；list_memories() 全量取出后走 embedding 召回 Top-5。

2026-07-31：改用 JSON 输出，用户能看到具体注入了什么（新增） 以前直接 print("\n".join(sections))，三段内容确实进了 Claude 的上下文，但用户在界面上完全看不到任何提示——不知道 这次到底召回了哪些习惯/记忆。改成输出 JSON：{"systemMessage": "...", "hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "..."}}。additionalContext 是三段拼接后的原文，跟以前给 Claude 看的内容完全一致； systemMessage（hooks 通用字段，所有事件都会展示给用户）是新加的一份高亮摘要——按类别列计数， 每一条都完整展示、不截断/不省略，多条内容逐行列出而不是堆在一行里，只在真正有内容注入时才输出。
孤儿 session 补漏：不阻塞会话启动 find_orphan_sessions() 找出"卡在 processing 超过 600s 且不是当前 session"的旧 session（这类 session 天然是"曾经在处理、但从未等到 release 就结束了"——如果达到过阈值/被强制刷新过就已经 release 了）。命中的话用临时文件承载 payload 当子进程 stdin、Popen() 起一个独立进程跑 summarize.py 的 mode=force，全程没有 write()/communicate()/wait() 等任何会阻塞的调用——真正的"发起后立刻返回"。这次注入用的可能是 "稍旧"的总结，孤儿内容补完后下一次会话才会读到。

05 情景记忆 · project-summary.md 滚动总结

阅读目的：理解这条新管线为什么数据源、存储模型、失败处理策略都跟 instinct/memory 管线刻意不同。

--resume/--continue 能找回完整历史，但要重新加载整段 transcript，首次 token 消耗很大。这条管线的目标是： 持续把对话内容（用户输入 + assistant 最终回复）滚动总结成单份、持续演进的项目工作记忆文档，新会话启动时自动注入， 不需要手动 --resume。

数据源：直接解析 transcript JSONL

memory_lib/transcript.py 的 parse_new_turns(transcript_path, after_uuid) 读 Claude Code 自己写的 transcript 文件，按状态机顺序扫描：遇到真实用户消息（type=="user" 且 message.content 是字符串） 开启新轮次；随后每条 type=="assistant" 记录只取 content 数组里 type=="text" 的块依次拼接，直到下一条 真实用户消息才 flush——工具结果伪装成 user 角色（content 是数组）和穿插的 tool_use 块都被正确过滤/跳过。 单轮文本超过 4000 字符截断。这是未文档化的内部格式（对照 UserPromptSubmit+last_assistant_message 两个 官方字段拼接的方案后，权衡"能拿到工具调用细节"选择了 transcript 解析，接受升级可能破坏解析的风险）。

触发：数量阈值 + PreCompact + SessionEnd 三重

Stop 常规触发只在累计新增轮次 ≥ _TURN_THRESHOLD(100) 时才真正总结，未达阈值时不 release，游标停在 processing 留到下次累积。PreCompact（内容即将被压缩前）和 SessionEnd（会话正常终止）都是 force 模式， 跳过阈值判断，只要有新增轮次就总结——PreCompact 保证"真正要丢内容之前"必有一次总结，SessionEnd 保证正常退出时不留尾巴。

失败处理：跟 extract.py 刻意不同的取舍

cursor 只在总结成功写入后才推进 extract.py 的哲学是"丢了就丢了，行为习惯会反复出现，下次还能学到"；但对话内容是一次性的，这批 turns 一旦被跳过就 再也不会出现在总结里。所以 summarize.py 的 LLM 调用失败时，release_session 传回的是本批开始前的原始 cursor，下次触发重试同一批内容，而不是像 extract.py 那样无条件推进丢弃。

实现过程中发现并修复的设计缺陷

transcript_store.try_claim_session() 最初对"全新 session"（claim 成功，cursor 恰好是 None）和"锁被占用未超时" （claim 失败，应该跳过）这两种语义完全不同的场景都返回 None，调用方无法区分——每个新 session 的第一次总结都会因此卡死。 已改成显式的 (claimed: bool, cursor: str | None) 元组返回，从根上消除歧义。

06 流程挖掘 · mine_procedures.py（Stop）

阅读目的：理解为什么"多步骤有序流程"不能直接塞进 instinct 机制，以及"复现频率"和"是否正确"这两件事是怎么被拆开衡量的。

动机来自真实观察：同一类任务（比如"写含 mermaid 图的 md 文档，再转成带图片的 html"）在不同会话里，实际执行的工具调用序列高度相似。 hook 拿不到模型的原始思维链（不稳定、不建议作为数据源），但能稳定拿到的是 工具调用序列（observe.py 已记录）和 assistant 文本（transcript.py 已能解析）——这条管线就是把这两样东西按"用户轮次"切成 episode，喂给 LLM 识别 是否构成"值得记住的多步骤可复用流程"，新增一种独立记忆类型 procedure（跟 instinct 的单条 trigger→action 规则不同， 是有序步骤列表），复用 instinct 现成的 confidence 演化机制来判断何时"够格晋升"。

2026-07-30 修正：只看复现次数不够，还得判断这次复现是否真的有效 最初版本里 hit_count/confidence 只反映"这个流程复现了几次"，从不判断"这次复现的结果是否真的解决了问题"—— 一个反复被模型给出但实际没用的流程，一样会被无脑加分直至晋升。修正方案两层：自动层用"下一轮用户消息"作为信号 （这个数据 transcript.parse_new_turns 已经有，不用新采集），LLM 结合它判断 is_successful（用户是否在纠正/拒绝这个方案）， 接着 confidence = update_confidence(prior, hit=is_successful)——不成功时真的会扣分（复用 confidence.py 现成的 MISS_DELTA，之前从未被调用过）。人工层兜底：转 Skill 确认时一并问"这个流程是否正确"，答"不正确"就标记 status=deprecated，不执行转换。

episode 边界的连带调整：判断 is_successful 需要看"下一轮用户反馈"，所以每个 episode 必须存在下一轮才能处理—— 处理范围从"全部轮次"收窄为 range(len(new_turns) - 1)，最后一轮留到下次 Stop（届时会出现新的下一轮）。游标推进也相应改成条件式： 轮次数 <2 时完全不 release（跟 summarize.py 未达阈值时"不release、留到下次累积"是同一处理哲学）； 够处理时 release 到 new_turns[-2].uuid 而不是最后一条，避免最后一轮被跳过丢失。

晋升即高亮，不做上下文注入：procedure 一旦 confidence≥PROMOTE_THRESHOLD 首次跨过阈值，就通过 hook 输出 JSON 的 systemMessage 字段提示用户（Stop 事件的普通 stdout 不会展示给用户，systemMessage 是唯一能让用户在 Stop 场景看到提示的机制）—— 刻意不像 instinct 那样注入每次 SessionStart 上下文，procedure 内容比一行 trigger 重得多，用户自己决定要不要看。

生成 SKILL.md 不是新增的自动化代码——是 Claude 在对话里用 Read/Write 工具完成的正常操作，套用项目里已有 Skill 的 frontmatter 格式（name + description）。deprecated 的 procedure 如果后续又被 find_similar_procedure 命中，会"复活"为 candidate 重新参与晋升判断（skill_asked 也重置）， 跟 instinct 命中已 deprecated 条目时的处理逻辑一致。

当前真实数据：memory/procedures/ 下 4 条候选，全部还是 status=candidate， 还没有一条在真实使用中稳定复现到跨过晋升阈值——这是预期状态，晋升本来就需要多次真实复现才会发生。

07 最近会话记录 · record_session.py（SessionEnd）

阅读目的：确认这个小工具解决的是"记不住 session_id"这个具体痛点，跟 project-summary.md 的关系是什么。

Claude Code 退出时会提示"可以用 --resume <session_id> 恢复"，但 hook 拦不到、改不了 CLI 自己打印的那句提示。 能做的是在 SessionEnd 时把 session_id、退出时间、内容摘要记进一份本地文件，用户想 resume 时自己去查—— 不做 SessionStart 注入（用户明确要求不需要，靠自己翻文件）。

沿用项目里已有的"隐藏 JSON 存真实数据 + 全量重新渲染人类可读 md"模式（对照 storage.py 的 .dedup_state.json + regenerate_rules_file()）：memory/.recent-sessions.json 是真正数据源， 按 session_id upsert（同一 session 多次退出更新而非重复追加），按 last_exit_ts 降序裁剪到最多 10 条； 每次都重新渲染成 memory/recent-sessions.md。summary_excerpt 直接取当前 project-summary.md 内容截断到约 200 字符——不强求跨脚本执行顺序（record_session.py 独立于 summarize.py 读写各自的文件， 读到的可能是这次退出前最新的一版，够用即可）。

两个产物文件都不进 git：session_id 只在本机有意义（resume 依赖本机的 transcript 文件）， 跟 .dedup_state.json/sqlite 状态文件性质一样是本地运行状态。SessionEnd 不保证在 crash/kill 时触发， 跟 project-summary.md 现有的限制一致。

09 存储层：文件 vs SQLite

阅读目的：说明为什么同一个系统里一部分数据用 git 可追踪的 markdown，一部分用 SQLite，不是随意选择。

路径形式git 追踪为什么
instincts/ / memories/ / rules/auto-evolved.mdYAML frontmatter + Markdown是要能 git diff 看行为习惯怎么演化、能手工打开改一条记录，可读性优先
project-summary.md纯 Markdown 叙述文本是持续演进的单份总结，人可读可 review，跟其余可提交数据同等对待
procedures/*.mdYAML frontmatter + Markdown是多步骤流程记录，同样要能 diff 看演化、手工打开改一条
.observations.sqlite3SQLite（observations + session_progress 两表）否高频追加、纯行为信号、从不给人看；原 jsonl 手写轮转逻辑复杂度和收益不成正比
.transcript_progress.sqlite3SQLite（session_progress 表，含 transcript_path）否情景记忆管线独立的游标状态，跟语义记忆管线的游标是两套互不共享的表
.procedure_progress.sqlite3SQLite（procedure_progress 表）否流程挖掘管线自己独立的游标状态，跟前两条管线的游标都不共享
.vector_cache.sqlite3SQLite + sqlite-vec 扩展否embedding 结果缓存，按 memory_id + 内容哈希失效，纯派生数据，可随时重建
.dedup_state.json纯 JSON否observe.py 的短期防抖动状态
.recent-sessions.json + recent-sessions.mdJSON + 渲染出的 Markdown否session_id 只在本机有意义（resume 依赖本机 transcript 文件），纯本地状态

.gitignore 用通配符 memory/.*.sqlite3 统一忽略所有运行时 SQLite 文件， 不用每加一个新缓存/状态文件都手动改一行。

10 置信度演化

阅读目的：确认命中/未命中如何量化影响 confidence，以及晋升/废弃两个阈值的实际效果。

常量值含义
INITIAL_CONFIDENCE0.5新建 instinct/procedure 的起始值
HIT_DELTA+0.05命中一次的增量
MISS_DELTA-0.05未命中/不成功一次的增量（procedure 的 is_successful=false 会真正触发这条路径，之前从未被调用过）
CONFIDENCE_CAP0.9命中不会超过这个上限
PROMOTE_THRESHOLD0.7≥ 此值才会被 regenerate_rules_file 收进规则文件被注入，或 procedure 晋升为 promoted
DEPRECATE_THRESHOLD0.55< 此值标记 deprecated: true（instinct 的自动衰减机制本身当前已停用，见 §3；procedure 走人工兜底标记，见 §6）
RULES_LIMIT30规则文件/注入的 instinct 条数硬上限
_TURN_THRESHOLD100情景记忆 Stop 常规触发的轮次阈值（PreCompact/SessionEnd 跳过此判断）
STALE_PROCESSING_SECONDS600三条管线的并发锁 / 孤儿判定共用这个超时值

procedure 完全复用 instinct 这套常量和 update_confidence() 函数，没有单独开一套配置—— 新建候选也统一走 update_confidence(INITIAL_CONFIDENCE, hit=is_successful)，不是无条件从 0.5 起步，这样首次就失败也能立刻扣分。

11 Provider 降级矩阵

阅读目的：确认没有配置任何 API Key 时三条管线是否还能跑通（能，只是精度打折，流程挖掘会整个停摆而非降级——见下方 NullProvider 说明）。

LLM：get_llm_provider()

DEEPSEEK_API_KEY 非空 → DeepSeekProvider（OpenAI 兼容 /chat/completions，10s 超时）。 否则 → NullProvider：不发请求，只用 \b 词边界正则匹配 pnpm/npm/yarn，只能产出 project_facts。

LLM 第二能力：summarize_conversation()

DeepSeekProvider 失败时抛异常（不是静默返回空串）——让 summarize.py 能感知失败、 不推进 cursor。NullProvider 原样返回 previous_summary：没有真正总结能力，但至少不丢已有总结。

LLM 第三能力：mine_procedure()（新增）

DeepSeekProvider 同样是请求/解析失败抛异常，由 mine_procedures.py 逐 episode 兜底、不中断整批。 NullProvider 恒返回 None——流程挖掘是纯语义判断，规则匹配识别不出"这段操作是否值得记住"，没有 LLM 时干脆不挖掘。

Embedding：get_embedding_provider()

ARK_API_KEY 非空时先探活（embed(["ping"])，5s 超时），成功 → ArkProvider （SUPPORTS_CACHE=True，走 sqlite-vec 缓存）；探活失败或未配置 → TfidfProvider （本地 sklearn，每次现场 fit，不缓存）。
